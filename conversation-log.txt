## What Anthropic Is Already Trying

Anthropic's current approach is a patchwork of pragmatic mitigations, not a
unified architecture:

### Layer 1: Static Context Injection (CLAUDE.md)

CLAUDE.md files at project, user, and org scope are auto-loaded on session
start. First 200 lines of auto-accumulated notes also injected.

Limitation: This is declarative knowledge ("always use pytest"), not episodic
memory ("yesterday I refactored the auth module"). It can't capture the state
of a multi-session task.

### Layer 2: On-Demand Memory Tool (API)

Claude has access to a /memories directory where it can create, read, update,
and delete files across conversations. Implements "just-in-time retrieval."

Critical weakness: Claude has to recognize when historical context is relevant.
This is a meta-cognitive task that the model frequently fails at. If Claude
doesn't think to check, the memory is useless.

### Layer 3: Three-Tier Context Compaction

1. Microcompaction -- Large tool outputs offloaded to disk early
2. Auto-compaction -- When free context drops below headroom, generates
   structured summary and drops everything before it
3. Manual compaction -- User-triggered with optional focus hints

Fundamental failure mode: Compaction is lossy summarization. The model doing
the compaction doesn't know what will be important in the future.

### Layer 4: Two-Agent Architecture (Agent SDK)

- Initializer Agent -- Sets up environment, structures project, creates plan
- Coding Agent -- Operates in subsequent sessions, makes incremental progress

Key insight: Reframes from "give one agent infinite memory" to "structure work
so each session can start from a clean state." It's a process solution, not a
memory solution.

Limitation: Depends on quality of handoff artifact. Only works for neatly
decomposable tasks, not messy debugging/exploration.

### Layer 5: Checkpoints and Rewinding

File-level snapshots before every write operation.

Critical gap: File rewinding restores files on disk but does not rewind the
conversation. Claude's context still contains the memory of having made and
then undone the change.

### Layer 6: Subagent Isolation

Subagents maintain separate context windows for focused subtasks.

Limitation: Subagents are ephemeral. When complete, only final output returns
to parent. The reasoning and learned context are lost.

### The Fundamental Gap

All solutions share a common assumption: the context window is the primary
workspace, and everything else is a workaround. There is no persistent,
structured, queryable representation of an agent's accumulated understanding.


## The Biological Lens

### The Brain's Memory Architecture

The brain operates on Complementary Learning Systems (CLS) theory:

| Brain System        | Function                                    | AI Analog                |
|---------------------|---------------------------------------------|--------------------------|
| Hippocampus         | Fast learning, episodic memory              | Context window           |
| Neocortex           | Slow learning, semantic memory              | Model weights            |
| Prefrontal Cortex   | Working memory, executive control           | System prompt + planning |
| Sleep replay        | Consolidates hippocampal → neocortical      | ??? (nothing)            |

The critical missing piece: the consolidation process -- the mechanism that
transforms raw episodic experience into structured, durable, retrievable
knowledge.

### Five Biological Principles That Map to the Problem

1. ENCODING SPECIFICITY + PATTERN SEPARATION (Hippocampal Dentate Gyrus)

The brain creates sparse, distinct representations even for similar
experiences. AI problem: When Claude compacts context, similar-looking code
changes get merged into vague summaries. A pattern-separation mechanism would
maintain distinct episodic traces.

2. CONSOLIDATION IS SELECTIVE, NOT COMPLETE (Sleep Replay)

During sleep, only memories that aid generalization consolidate to the
neocortex. AI problem: Current compaction treats all context equally. A
biologically-inspired system would have an offline "consolidation" phase that
promotes generalizable knowledge, decays episode-specific details, and
actively suppresses wrong information.

3. RETRIEVAL IS CUE-DEPENDENT AND RECONSTRUCTIVE (Hippocampal CA3)

Human memory is pattern completion, not lookup. Given a partial cue, the
hippocampal CA3 region reconstructs the full memory. AI problem: Claude's
memory tool requires explicit retrieval decisions. A cue-dependent system
would automatically activate relevant memories when the current context
resembles a stored pattern.

4. MEMORY HAS MULTIPLE TIMESCALES (Synaptic vs. Systems Consolidation)

The brain operates on at least three timescales:
- Immediate (milliseconds): Synaptic activation = current context window
- Short-term (minutes to hours): Hippocampal trace = within-session memory
- Long-term (days to years): Neocortical integration = cross-session knowledge

Current Claude has only two. There's no intermediate timescale.

5. FORGETTING IS FUNCTIONAL (Interference Theory + Active Forgetting)

The brain actively forgets. Irrelevant details are suppressed so relevant
memories can be retrieved more quickly. AI problem: Claude Code's memory files
grow monotonically. A biologically-inspired system would decay memories based
on recency, frequency, and relevance.

### Proposed Biologically-Inspired Architecture

    ┌─────────────────────────────────────────────────────┐
    │                  WORKING MEMORY                      │
    │            (Context Window ~200K tokens)              │
    │  Current task, active reasoning, immediate tool I/O  │
    └────────────────────┬────────────────────────────────┘
                         │ encode (during session)
                         ▼
    ┌─────────────────────────────────────────────────────┐
    │              EPISODIC BUFFER                         │
    │         (Structured Session Traces)                  │
    │  Per-session: goals, decisions, diffs, errors,       │
    │  reasoning chains. Indexed by task/file/concept.     │
    │  Survives compaction. Decays over sessions.          │
    └────────────────────┬────────────────────────────────┘
                         │ consolidate (between sessions / "sleep")
                         ▼
    ┌─────────────────────────────────────────────────────┐
    │             SEMANTIC MEMORY                          │
    │        (Project Knowledge Graph)                     │
    │  Architectural decisions, code patterns, learned     │
    │  preferences, dependency relationships.              │
    │  Queryable by cue-based pattern matching.            │
    │  Grows slowly. Actively prunes contradictions.       │
    └────────────────────┬────────────────────────────────┘
                         │ prime (on session start)
                         ▼
    ┌─────────────────────────────────────────────────────┐
    │            PROCEDURAL MEMORY                         │
    │           (CLAUDE.md + Learned Habits)               │
    │  "How to" knowledge: build commands, test patterns,  │
    │  code style, team conventions. Always loaded.        │
    └─────────────────────────────────────────────────────┘

Key innovations:
1. Episodic Buffer -- structured, indexed event log, richer than compaction
2. Consolidation Process -- offline "sleep" step between sessions
3. Cue-Based Retrieval -- automatic, orchestrator-driven memory surfacing
4. Active Forgetting -- salience decay to keep memory lean and relevant

## Step 1: What Actually Happens When You Use Claude Code Today

When you start a Claude Code session, the system creates a context window --
a single, fixed-size notepad. On Claude Sonnet 4.5/4.6, this notepad has
room for roughly 200,000 tokens (about 150,000 words).

EVERYTHING goes on this one notepad:
- The system prompt (Claude's instructions, tool definitions)
- Your messages
- Claude's responses
- Every file Claude reads (full contents)
- Every command Claude runs and its output
- Every file Claude writes or edits

The notepad does not grow. When it fills up, you're stuck.

## Step 1b: What the Context Window Actually Looks Like

The context window is literally a list of messages -- a JSON array that gets
sent to the Claude API on every single turn:

    [
      {"role": "system", "content": "You are Claude Code...tools: Read, Write..."},
      {"role": "system", "content": "[CLAUDE.md contents]"},
      {"role": "user", "content": "Fix the login bug in our auth module"},
      {"role": "assistant", "content": "I'll investigate...",
       "tool_calls": [{"tool": "Read", "args": {"path": "src/auth.py"}}]},
      {"role": "tool", "content": "# src/auth.py\nimport jwt\n... [ENTIRE FILE] ..."},
      {"role": "assistant", "content": "I see the issue on line 42...",
       "tool_calls": [{"tool": "Bash", "args": {"command": "pytest tests/"}}]},
      {"role": "tool", "content": "FAILED tests/test_auth.py..."},
      {"role": "assistant", "content": "Let me fix it.",
       "tool_calls": [{"tool": "Edit", "args": {...}}]}
    ]

Critical: Claude is STATELESS. It doesn't "remember" anything between turns.
Every time you send a new message, the ENTIRE array gets sent to the API.
Claude reads the whole thing from scratch, generates a response, and that
response gets appended. The context window isn't "memory" -- it's the full
conversation transcript replayed to a fresh Claude instance every time.

## Step 1c: Where the 200K Tokens Actually Go

    200,000 tokens total
    ┌─────────────────────────────────────────────┐
    │  SYSTEM PROMPT + TOOL DEFINITIONS           │
    │  ~8,000-15,000 tokens                       │
    ├─────────────────────────────────────────────┤
    │  CLAUDE.md + AUTO MEMORY                    │
    │  ~1,000-5,000 tokens                        │
    ├─────────────────────────────────────────────┤
    │  CONVERSATION HISTORY                       │
    │  ~140,000-180,000 tokens                    │
    │  - Your messages                    ~5%     │
    │  - Claude's reasoning/responses    ~15%     │
    │  - File contents from reads        ~40%     │
    │  - Command outputs                 ~25%     │
    │  - Edit/write tool calls           ~15%     │
    ├─────────────────────────────────────────────┤
    │  RESERVED FOR OUTPUT                        │
    │  ~8,000-64,000 tokens                       │
    └─────────────────────────────────────────────┘

File reads are the biggest consumer. The useful reasoning is a minority (~20%).
The other ~80% is raw I/O artifacts -- file dumps and command outputs that were
useful for one step but are now dead weight.

## Step 1d: Why Claude Reads Whole Files

Three reasons:

1. Claude doesn't know what it needs until it sees it. The bug might be
   anywhere in the file.

2. Partial reads lose structural context. Without seeing imports, class
   definitions, or related methods, a fix might break other things.

3. The tool outputs are immutable in the transcript. Once 500 lines are read,
   those 500 lines are in the conversation array permanently. No mechanism to
   free those tokens except compaction.

The conversation transcript is an append-only log with no garbage collection.

Key contrast with biology: Your brain NEVER stores the raw sensory input. When
you read a file, your brain extracts meaning and discards the pixels. Claude
stores the pixels.

## Step 2: What Happens When the Notepad Fills Up -- Compaction

When the conversation array approaches ~190,000 tokens, Claude Code triggers
compaction:

1. Claude reads through the conversation history
2. Generates a structured summary
3. Everything before the compaction point gets DELETED
4. The summary gets inserted as a compaction block
5. Recent files and task state get "rehydrated" (re-read)

After compaction: ~40,000 tokens used, lots of room again.

### Why This Breaks

The summary is LOSSY. What gets lost:
- Failed approaches (so Claude tries them again)
- Specific diffs (Claude knows it "fixed auth.py" but not how)
- Reasoning chains (the WHY behind decisions evaporates)
- Relationships between changes

Claude post-compaction is like a person who had a concussion mid-project.

## Step 2b: The Compaction Prompt

When compaction triggers, a separate API call is made with a prompt like:

    System: You are summarizing a conversation to preserve essential context
    while reducing token count. Your summary will replace the conversation
    history, so you must preserve:
    - The user's original goals and current task state
    - Key decisions made and their reasoning
    - What files were modified and how
    - Any errors encountered and how they were resolved
    - Current work in progress

Claude generates a compaction block like:

    <compaction>
    ## Task Context
    User is building a REST API for a task management app.

    ## Completed Work
    - Set up Express.js project with TypeScript
    - Created User model in src/models/user.ts
    - Implemented POST /auth/login in src/routes/auth.ts
    - Fixed bug: token refresh was not working (changed line 42)

    ## Current Task
    Implementing rate limiting on the login endpoint using Redis.

    ## Key Decisions
    - Chose JWT over sessions for stateless auth
    - Using PostgreSQL with Prisma ORM

    ## Active Files
    - src/routes/auth.ts (last modified)
    - src/models/user.ts
    </compaction>

Notice what's lost vs captured:

Captured: "Fixed bug: token refresh was not working (changed line 42)"

Lost:
- WHY it wasn't working (specific wrong value, root cause)
- The 3 other files read during investigation that were irrelevant
- The fact that Claude tried a different fix first that broke tests
- The specific test output that confirmed the fix
- The user's comment "we might switch to OAuth later"

## Step 2c: Why "Better Compaction Prompts" Have a Ceiling

Four hard limits:

1. The summary itself costs tokens. More detail = longer summary = less space
   recovered. Zero-sum tradeoff.

2. The model compacting doesn't know the future. It has to guess what will
   matter, and frequently guesses wrong.

3. Compaction compounds. Summary of a summary of a summary. Like telephone --
   signal degrades with each pass.

4. It's a single text blob. No way to retrieve just one part. All or nothing.

Better prompts treat the symptom (bad summaries), not the disease (memory as
a single unstructured text buffer with lossy compression as the only
reclamation strategy).

## Step 3: The Multi-Session Problem

When you close Claude Code and open it tomorrow, something far more drastic
happens: The entire context window is gone. Completely. Zero.

A new session starts with:
1. System prompt (~10K tokens)
2. CLAUDE.md contents (~1-5K tokens)
3. Auto-memory notes (~1-2K tokens)
4. Your first message

~190,000 tokens of working context from yesterday -- gone. Not summarized.
Not compressed. DELETED.

### The Result Across Sessions

Session 1: Claude understands full context. Great work. Session ends.
Session 2: "I'm Claude, how can I help?" Re-explain everything. 20 min lost.
Session 3: Claude doesn't know about abandoned approaches. Tries them again.
Session 4: Claude contradicts architectural decisions from Session 2.
Session 5: Developer gives up on continuity. Writes extensive re-prompts.

The developer becomes the memory system.

## Step 3b: Plan Mode vs. Two-Agent Architecture

Plan Mode is a mode WITHIN a single session. Claude switches to read-only,
researches, produces a plan as text in the same context window, then switches
back to Agent mode. When the session ends, the plan disappears.

The Two-Agent Architecture is a multi-process, multi-session pattern:

    ┌─────────────────────┐
    │  INITIALIZER AGENT  │  ← Separate Claude instance
    │  - Analyzes repo    │
    │  - Creates plan     │
    │  - Writes plan to   │──── plan.md, progress.md (files on disk)
    │    disk as files    │
    └─────────────────────┘
             │ (session ends, context window destroyed)
             ▼ (new session, new context window)
    ┌─────────────────────┐
    │   CODING AGENT #1   │  ← Different Claude instance, fresh context
    │  - Reads plan.md    │◄─── reads files from disk
    │  - Works on step 1  │
    │  - Updates progress │──── writes progress back to disk
    └─────────────────────┘
             │ (session ends, context window destroyed)
             ▼ (new session)
    ┌─────────────────────┐
    │   CODING AGENT #2   │
    │  - Reads plan.md    │◄─── reads files from disk
    │  - Reads progress   │
    │  - Works on step 2  │
    └─────────────────────┘

The two-agent pattern uses FILES ON DISK as the memory bridge. "Disk" = regular
files saved to your filesystem, like source code. plan.md is a markdown file
Claude writes using the Write tool. The next session reads it with the Read tool.

All of Anthropic's cross-session memory solutions ultimately reduce to:
WRITE A FILE, HOPE THE NEXT SESSION READS IT.

## Step 3c-3e: Plan Mode, Permissions, and Structured Questions

Three separate interactive mechanisms in Cursor/Claude Code:

1. Permission Prompts -- approve/deny popups when Claude wants to write/edit/
   run commands. Safety gate. Not related to planning.

2. Plan Mode -- read-only research phase. Claude reads files, thinks, presents
   a plan. Just text in the context window.

3. Structured Questions (AskQuestion tool) -- The multiple-choice UI cards you
   see are NOT Claude writing "pick A or B." It's Claude making a TOOL CALL to
   AskQuestion. The orchestrator renders it as a UI widget. Your click becomes
   a tool result string that flows back into the conversation array.

None of these persist across sessions.

## Step 3f: Full Prompt Flow for AskQuestion

Phase 1: You type "Build me a REST API for task management"

Phase 2: Orchestrator builds messages array:
    [system_prompt (includes AskQuestion tool definition), your_message]

Phase 3: Claude processes and thinks: "User hasn't specified language or DB.
    This has multiple valid approaches. I should gather preferences."
    This decision is entirely the model's judgment based on system prompt

Phase 4: Claude returns a tool call:

Every tool follows this exact same loop. The only thing that varies is what

## The Orchestrator is Code, Not a Prompt

The orchestrator is REGULAR CODE -- TypeScript/Python running on your machine.
It is NOT an LLM. It doesn't think. It follows deterministic rules:

    messages = [system_prompt, claude_md_content]
    available_tools = ALL_TOOLS

    while True:
        user_input = get_user_input()
        messages.append({"role": "user", "content": user_input})

        while True:
            response = claude_api.call(messages=messages, tools=available_tools)
            messages.append(response)

            if not response.tool_calls:
                display_to_user(response.content)
                break

            for tool_call in response.tool_calls:
                if tool_call.name == "Read":
                    result = read_file(tool_call.args["path"])
                elif tool_call.name == "Bash":
                    if user_approves(tool_call):
                        result = run_command(tool_call.args["command"])
                elif tool_call.name == "AskQuestion":
                    result = show_ui_cards_and_wait(tool_call.args)
                elif tool_call.name == "SwitchMode":
                    if tool_call.args["mode"] == "plan":
                        available_tools = READ_ONLY_TOOLS
                    else:
                        available_tools = ALL_TOOLS
                    result = "Mode switched"

                messages.append({"role": "tool", "content": result})

Claude is the brain. The orchestrator is the hands.

## Step 4: The Biological Memory System

### Your Brain's Three Memory Systems

Working Memory (Prefrontal Cortex) -- capacity: ~4-7 items
Your "context window." Tiny capacity, constantly overwriting.

Episodic Memory (Hippocampus) -- capacity: enormous, but decays
Stores experiences -- specific events with context. "Yesterday I was debugging
the auth module. I tried changing the token expiry but that broke the tests."
These are indexed by context -- seeing the same codebase automatically triggers
recall of related episodes.

Semantic Memory (Neocortex) -- capacity: vast, very durable
Stores knowledge -- facts and patterns stripped from specific episodes. "JWT
tokens need a refresh mechanism." You don't remember WHEN you learned these
things, but you know them.

### The Critical Process: Consolidation

    During the day (while working):
    Sensory input → WORKING MEMORY (hold ~4 items)
                         │
                         │ encode (important things get flagged)
                         ▼
                   EPISODIC MEMORY (hippocampus stores the experience)

    During sleep (offline consolidation):
    EPISODIC MEMORY
         │
         │ replay (hippocampus reactivates stored experiences)
         │
         ├── Does this episode help me generalize?
         │       YES → consolidate to SEMANTIC MEMORY (neocortex)
         │       NO  → let it decay (active forgetting)
         │
         └── Is this episode contradicted by newer experience?
                 YES → suppress it (interference resolution)
                 NO  → keep it accessible

    Next morning (retrieval):
    Current context (what you see/hear/think)
         │
         │ pattern match (automatic, not deliberate)
         │
         ├── matches EPISODIC MEMORY → "I remember debugging this yesterday"
         └── matches SEMANTIC MEMORY → "I know this pattern, JWT needs..."
                  │
                  ▼
            WORKING MEMORY (relevant memories loaded alongside current task)

### Three Properties That Claude Lacks Entirely

1. Encoding is selective, not total. Your brain extracts meaning and discards
   raw input. Claude stores everything verbatim.

2. Retrieval is automatic and cue-driven. Similar context automatically
   triggers related memories. Claude has to explicitly call a memory tool.

3. Consolidation transforms memories. Sleep doesn't just store -- it
   transforms specific episodes into general knowledge. Claude's compaction
   summarizes but doesn't abstract or generalize.

## Step 5: Applying the Biological Architecture to Claude

### Component 1: The Episodic Buffer (Replacing Compaction)

Instead of compaction writing a paragraph, the orchestrator maintains a
structured episodic store -- a local database or JSON file. During a session,
every significant action gets encoded as a structured episode:

    // episodes.jsonl -- one entry per significant action
    {"session": 3, "timestamp": "2026-03-02T14:23:00", "type": "investigation",
     "goal": "fix login bug", "file": "src/auth.py", "lines": "40-58",
     "observation": "token expiry hardcoded to 3600, should use config value",

### Component 2: Cue-Based Retrieval (Replacing Manual Memory Lookup)

The orchestrator runs a retrieval step BEFORE every API call -- not triggered
by Claude, but by the orchestrator itself:

    # Modified orchestrator loop
    while True:
        user_input = get_user_input()

        # ★ CUE-BASED RETRIEVAL: search episodic store before calling Claude
        current_cues = extract_cues(user_input, active_files, recent_context)
        relevant_episodes = episodic_store.search(current_cues, top_k=5)

        # ★ Inject as a special context block
        episode_context = format_episodes(relevant_episodes)

        messages.append({
            "role": "system",
            "content": f"Relevant history from previous sessions:\n{episode_context}"
        })
        messages.append({"role": "user", "content": user_input})

        response = call_claude_api(messages, tools)
        # ... rest of loop as before

Claude never has to "decide" to remember. The orchestrator does the remembering
FOR it, the same way your hippocampus surfaces memories without conscious effort.

### Component 3: Consolidation (The "Sleep" Process)

When a session ends, the orchestrator runs a consolidation step -- a separate,
cheap Claude API call:

    def consolidate():
        new_episodes = episodic_store.get_session(current_session_id)
        existing_knowledge = semantic_store.read_all()

        consolidation_prompt = f"""
        Review these new work episodes and existing project knowledge.

        New episodes: {new_episodes}
        Existing knowledge: {existing_knowledge}

        1. What patterns appear across multiple episodes? Promote to knowledge.
        2. What existing knowledge is contradicted by new episodes? Update it.
        3. What episodes are one-off details unlikely to matter? Mark for decay.
        """

        result = call_claude_api(model="haiku", messages=[consolidation_prompt])

        semantic_store.update(result.new_knowledge)
        episodic_store.decay(result.episodes_to_forget)

### Component 4: Active Forgetting (Preventing Memory Bloat)

Every episode and knowledge entry has a salience score that decays over time
and increases when accessed:

    {"episode_id": "ep_042", "salience": 0.92, "last_accessed": "2026-03-02",
     "access_count": 4, "content": "..."}

    {"episode_id": "ep_003", "salience": 0.12, "last_accessed": "2026-02-15",
     "access_count": 1, "content": "..."}

Episodes below threshold get pruned during consolidation. Memory stays lean.

          ▼
    Claude API call → response (text or tool call)
          │
          ▼
    ★ Episode encoding: orchestrator logs structured episode to episodic store
          │
          ▼
    Tool execution (if needed) → result appended → loop back
          │
          ▼
    If context getting full:
      ★ Smart compaction: drop raw tool outputs, keep episode references
      (episodes live in external store, not in context window)

    SESSION END
    ───────────
    ★ Consolidation ("sleep"):
      ├── Replay episodes from this session
      ├── Identify generalizable patterns → promote to semantic store
      ├── Identify contradicted knowledge → update semantic store
      ├── Decay low-salience episodes → prune episodic store
      └── Update salience scores
